LPA*

Алгоритм №8 — «живучий» A*: не считает заново то, что не изменилось

О чём вообще речь

Представь, что ты проложил маршрут по навигатору. На одной улице начали ремонт — перекрыли 100 метров. Обычный A* выбросит весь старый маршрут и пересчитает от нуля. LPA* скажет: «Так, я помню все расстояния. Перекрытие затрагивает 3 перекрёстка — пересчитаю только их, остальные 50 перекрёстков оставлю как есть». Результат тот же, работы — в 10 раз меньше.

LPA* (Lifelong Planning A*) — инкрементальная версия A*. При изменении карты не пересчитывает всё с нуля, а обновляет только затронутые узлы. Поиск идёт от старта к цели (в отличие от D* Lite, который ищет от цели к старту).

Ключевая идея: каждый узел хранит два значения — $g$ и $rhs$. Когда они равны, узел consistent. Когда нет — его надо пересчитать. При изменении карты становятся inconsistent только соседи изменённых клеток.

Два ключевых значения

$g(s)$ — текущая оценка

Как в обычном A*: стоимость кратчайшего найденного пути от старта до $s$.

$rhs(s)$ — «должно быть»

Одношаговый lookahead: минимум среди всех предшественников.

$$rhs(s) = \begin{cases} 0 & \text{если } s = s_{start} \\ \min_{s' \in Pred(s)} \big(g(s') + c(s', s)\big) & \text{иначе} \end{cases}$$

Consistency (согласованность):

  • Consistent: $g(s) = rhs(s)$ — узел в порядке, ничего делать не надо
  • Overconsistent: $g(s) > rhs(s)$ — нашёлся путь короче, обновляем $g$
  • Underconsistent: $g(s) < rhs(s)$ — старый путь стал хуже (стена!), увеличиваем $g$

Приоритетная очередь

Inconsistent узлы помещаются в очередь с ключом:

$$key(s) = \big[\min(g(s), rhs(s)) + h(s),\; \min(g(s), rhs(s))\big]$$

Двухкомпонентный ключ: первый элемент — как $f$ в A*, второй — для тай-брейка.

Как работает алгоритм

Фаза 1: Первый поиск (как A*)

1
Инициализация: $g(s) = \infty$, $rhs(s) = \infty$ для всех узлов. $rhs(start) = 0$. Добавляем старт в очередь.
2
Достаём узел с минимальным ключом. Если overconsistent ($g > rhs$): ставим $g = rhs$ (нашли кратчайший путь). Если underconsistent ($g < rhs$): ставим $g = \infty$ (обнуляем).
3
Обновляем $rhs$ соседей и добавляем inconsistent соседей в очередь.
4
Повторяем пока цель не станет consistent и ключ цели ≤ минимальному ключу в очереди.

Фаза 2: Изменение карты → инкрементальный пересчёт

5
Карта изменилась (новая стена). Обновляем $rhs$ только для соседей изменённых клеток.
6
Помечаем эти узлы как inconsistent, добавляем в очередь.
7
Запускаем ComputeShortestPath() — она обновит только «волну» от изменений, не трогая остальных.

LPA* vs D* Lite

D* Lite = LPA* «наоборот». Оба используют g/rhs, оба инкрементальные. Но:

АспектLPA*D* Lite
Направление поиска Старт → Цель Цель → Старт
Когда полезен Старт фиксирован, карта меняется Робот движется, карта меняется
Кто обновляет путь Внешний наблюдатель (e.g. сервер) Сам робот на ходу
Применение в ROS2 Статический планировщик с апдейтами карты Nav2 planner для мобильного робота

Псевдокод

function Initialize():
    for all s ∈ S:
        g(s) ← ∞;  rhs(s) ← ∞
    rhs(s_start) ← 0
    U.insert(s_start, CalcKey(s_start))

function CalcKey(s):
    return [min(g(s), rhs(s)) + h(s, s_goal),  min(g(s), rhs(s))]

function UpdateVertex(u):
    if u ≠ s_start:
        rhs(u) ← min over predecessors s': g(s') + c(s', u)
    if u ∈ U: U.remove(u)
    if g(u) ≠ rhs(u): U.insert(u, CalcKey(u))

function ComputeShortestPath():
    while U.topKey() < CalcKey(s_goal) or rhs(s_goal) ≠ g(s_goal):
        u ← U.pop()
        if g(u) > rhs(u):        // overconsistent
            g(u) ← rhs(u)
            for all s ∈ Succ(u): UpdateVertex(s)
        else:                     // underconsistent
            g(u) ← ∞
            for all s ∈ Succ(u) ∪ {u}: UpdateVertex(s)

function Main():
    Initialize()
    ComputeShortestPath()      // первый поиск
    while карта меняется:
        for каждого изменённого ребра (u, v):
            обнови c(u, v)
            UpdateVertex(v)
        ComputeShortestPath()   // инкрементальный пересчёт

Реализация в C++ (ROS2)

Основные структуры и функция инкрементального обновления. Остальной код A* переиспользуется.

// --- lpa_star.hpp ---
#include <unordered_map>
#include <queue>

struct LPANode {
    int x, y;
    double g = 1e9, rhs = 1e9;
    std::pair<double,double> key() const {
        double m = std::min(g, rhs);
        return {m + heuristic(x, y, gx, gy), m};
    }
};

void update_vertex(LPANode& u) {
    if (u.x != sx || u.y != sy) {
        u.rhs = 1e9;
        for (auto& [nx, ny] : neighbors(u.x, u.y)) {
            if (!walkable(nx, ny)) continue;
            double cost = nodes[{nx,ny}].g + edge_cost(nx,ny,u.x,u.y);
            u.rhs = std::min(u.rhs, cost);
        }
    }
    open_list.erase(&u);  // удалить если есть
    if (u.g != u.rhs)
        open_list.insert(&u, u.key());
}

// При обнаружении новой стены на (wx, wy):
void on_wall_added(int wx, int wy) {
    grid[wy][wx] = WALL;
    for (auto& [nx, ny] : neighbors(wx, wy)) {
        update_vertex(nodes[{nx, ny}]);  // только соседи!
    }
    compute_shortest_path();  // инкрементально
}

Сложность

МетрикаЗначениеЧто это значит
Первый поиск $O(V \log V + E)$ Как A* — полный поиск от старта до цели
Инкрементальный $O(\Delta \log \Delta)$ $\Delta$ = число затронутых узлов. Обычно $\Delta \ll V$
Память $O(V)$ g и rhs для каждого узла + очередь

Когда использовать

Идеально для:

  • Централизованный планировщик (сервер знает всю карту)
  • Карта обновляется, но старт фиксирован
  • Частые мелкие изменения (строительство, блокировка дорог)
  • Серверная маршрутизация для нескольких роботов

Лучше выбрать D* Lite, если:

  • Робот движется и обнаруживает препятствия на ходу
  • Старт меняется каждый шаг (текущая позиция робота)
  • Нужна реакция в реальном времени на сенсоры

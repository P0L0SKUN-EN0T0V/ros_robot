D* Lite

Алгоритм №6 — навигация в меняющемся мире

О чём вообще речь

Все алгоритмы до этого предполагали, что карта статична — нарисовали стены, запустили поиск, нашли путь, поехали. Но реальный мир так не работает. Робот едет по коридору и вдруг — дверь закрылась. Или человек встал на пути. Или обвалился потолок (ладно, это для марсоходов).

Что делает A*? Весь путь — в мусорку, пересчитай заново. На маленькой карте это терпимо, но на карте 1000×1000 полный пересчёт занимает сотни миллисекунд. Робот стоит и ждёт.

D* Lite умеет пересчитывать путь инкрементально — обновляет только ту часть, которая затронута изменением. Дверь закрылась? Пересчитаем 20 клеток вокруг двери вместо 100 000 клеток всей карты.

Представь GPS-навигатор в машине. Ты едешь по маршруту, и вдруг дорога перекрыта. Навигатор не пересчитывает маршрут с нуля от дома — он только перестраивает кусок пути от текущей позиции. Это и есть D* Lite: «перепланируй минимум, используя то, что уже знаешь».
Главная идея: D* Lite ищет путь от цели к роботу (задом наперёд). Когда карта меняется около робота — нужно обновить только несколько узлов рядом с роботом, а не весь путь.

Почему «задом наперёд»?

Это самый контринтуитивный момент D* Lite. A* ищет путь от робота к цели. D* Lite — от цели к роботу. Зачем?

Подумай: робот движется вперёд, и изменения на карте происходят рядом с роботом (он видит новые препятствия своими сенсорами). Если дерево поиска растёт от цели — то изменения затрагивают только «листья» дерева (рядом с роботом), а не «корень» (цель). Обновить листья дешёво. Обновить корень — дорого.

Аналогия: представь дерево (настоящее). Если ветер обломит пару веточек на краю кроны — дерево в целом не изменилось. Но если подрубить ствол (корень) — упадёт всё. D* Lite ставит «корень» на цель, а «веточки» — у робота. Изменения карты = обломанные веточки, а не подрубленный ствол.

Математика

D* Lite основан на LPA* (алгоритм №8), который, в свою очередь, основан на Dijkstra. Здесь два ключевых значения для каждого узла:

1. Два типа стоимости: g и rhs

$$g(s) \text{ — текущая оценка расстояния от цели до } s$$
$$\text{rhs}(s) = \begin{cases} 0 & \text{если } s = \text{goal} \\ \min_{s' \in \text{succ}(s)} \left[ g(s') + c(s, s') \right] & \text{иначе} \end{cases}$$

$g(s)$ — это то, что мы думаем о расстоянии. $\text{rhs}(s)$ (right-hand side) — это то, что расстояние должно быть на основе соседей. Когда $g(s) = \text{rhs}(s)$ — узел согласован (consistent). Когда не равны — узел нужно обновить.

Представь бухгалтерию. g(s) — это «записано в журнале». rhs(s) — это «посчитано заново». Если совпадает — порядок. Если не совпадает — нужна ревизия. D* Lite делает ревизию только для «несовпадающих» записей, а не для всей бухгалтерии.

2. Ключ приоритета

Вместо простого $f(n)$ D* Lite использует двухкомпонентный ключ:

$$\text{key}(s) = \left[\; \min(g(s), \text{rhs}(s)) + h(s_\text{start}, s) + k_m, \;\; \min(g(s), \text{rhs}(s)) \;\right]$$

$k_m$ — накопленная поправка за перемещение робота. $h(s_\text{start}, s)$ — эвристика (расстояние от текущей позиции робота до $s$). Двухкомпонентный ключ нужен для корректного упорядочивания в priority queue.

3. Состояния узлов

СостояниеУсловиеЧто это значит
Consistent $g(s) = \text{rhs}(s)$ Узел актуален, пересчёт не нужен
Overconsistent $g(s) > \text{rhs}(s)$ Нашёлся более короткий путь — нужно уменьшить g(s)
Underconsistent $g(s) < \text{rhs}(s)$ Путь стал длиннее (препятствие появилось) — нужно увеличить g(s)

Как работает: пошагово

Фаза 1: Первоначальный поиск

1
Устанавливаем $g(\text{goal}) = \infty$, $\text{rhs}(\text{goal}) = 0$. Все остальные узлы: $g = \text{rhs} = \infty$.
2
Добавляем цель в priority queue (она единственная «несогласованная» — $g \neq \text{rhs}$).
3
Запускаем ComputeShortestPath() — обрабатываем узлы из очереди, пока стартовый узел не станет согласованным. Это похоже на обратный Dijkstra.
4
Путь найден. Робот начинает движение по пути (от старта к цели, следуя по минимальным g-значениям соседей).

Фаза 2: Обновление при изменении карты

5
Робот движется и сенсоры замечают изменение: новое препятствие или освободившаяся клетка.
6
Для каждой изменённой клетки пересчитываем $\text{rhs}$ и, если $g \neq \text{rhs}$, добавляем в priority queue.
7
Обновляем $k_m$ (поправку за перемещение робота).
8
Снова запускаем ComputeShortestPath() — но теперь она обрабатывает только несогласованные узлы (обычно их мало). Возвращаемся к шагу 5.

Что произошло:
  1. Этап 1: D* Lite нашёл путь (тот же, что и A*) — обход стены снизу
  2. Робот начал движение и дошёл до (0,1). Сенсоры обнаружили: (1,2) заблокирована!
  3. D* Lite пересчитал только 3 узла: (1,1), (0,1) и S. Их g-значения выросли
  4. Новый путь: от (0,1) идём вниз по столбцу 0, потом вправо по строке 3 → G
  5. Все остальные g-значения не изменились — в этом суть инкрементальности
A* пересчитал бы все ~20 узлов заново. D* Lite — только 2. На карте 1000×1000 это разница между 1 мс и 500 мс. Для робота на скорости 1 м/с — плавный объезд vs резкая остановка.

Псевдокод (упрощённый)

D_Star_Lite():
    // Инициализация
    for all s: g[s] = rhs[s] = INF
    rhs[goal] = 0
    U.insert(goal, calc_key(goal))
    k_m = 0
    s_last = s_start

    ComputeShortestPath()              // первоначальный поиск

    while s_start != goal:
        s_start = move_robot()         // робот двигается

        if map_changed():
            for each changed edge (u, v):
                update_cost(u, v)      // обновить стоимость ребра
                UpdateVertex(u)        // пересчитать rhs(u)

            k_m += h(s_last, s_start)  // поправка за перемещение
            s_last = s_start
            ComputeShortestPath()      // инкрементальный пересчёт


ComputeShortestPath():
    while U.top_key() < calc_key(s_start) OR rhs[s_start] != g[s_start]:
        u = U.pop()

        if g[u] > rhs[u]:             // overconsistent
            g[u] = rhs[u]             // уменьшаем g
            for each predecessor s of u:
                UpdateVertex(s)

        else:                          // underconsistent
            g[u] = INF                // сбрасываем g
            UpdateVertex(u)
            for each predecessor s of u:
                UpdateVertex(s)


UpdateVertex(u):
    if u != goal:
        rhs[u] = min over successors s' of [g[s'] + cost(u, s')]

    if u in U: U.remove(u)
    if g[u] != rhs[u]: U.insert(u, calc_key(u))
Ключевые идеи в коде:
  • ComputeShortestPath() — обрабатывает только несогласованные узлы ($g \neq \text{rhs}$)
  • При первом вызове — полный поиск (как Dijkstra от цели)
  • При последующих вызовах — только обновление затронутых узлов
  • k_m — компенсирует перемещение робота, чтобы не пересчитывать ключи всех узлов
  • Overconsistent ($g > \text{rhs}$) — путь стал короче, уменьшаем g
  • Underconsistent ($g < \text{rhs}$) — путь стал длиннее (новое препятствие), сбрасываем g

Сложность

МетрикаЗначениеПояснение
Первый поиск $O(N \log N)$ Как Dijkstra/A* — полный обход графа
Перепланирование $O(k \log k)$ $k$ — число затронутых узлов. Обычно $k \ll N$. Это главный выигрыш!
Память $O(N)$ g, rhs, key для каждого узла + priority queue
Полнота Полный Находит путь, если он существует
Оптимальность Оптимален Кратчайший путь гарантирован (как Dijkstra)

Интеграция с ROS2 (C++)

D* Lite идеально вписывается в ROS2-архитектуру: нода подписана на /map и при каждом обновлении карты инкрементально пересчитывает путь:

#include <rclcpp/rclcpp.hpp>
#include <nav_msgs/msg/occupancy_grid.hpp>
#include <nav_msgs/msg/path.hpp>
#include <queue>
#include <unordered_map>

class DStarLitePlanner : public rclcpp::Node {
public:
    DStarLitePlanner() : Node("dstar_lite_planner") {
        map_sub_ = this->create_subscription<nav_msgs::msg::OccupancyGrid>(
            "/map", 10, [this](nav_msgs::msg::OccupancyGrid::SharedPtr msg) {
                if (!initialized_) {
                    initialize(msg);
                    compute_shortest_path();
                    initialized_ = true;
                } else {
                    // Инкрементальное обновление!
                    auto changes = detect_changes(old_map_, msg);
                    if (!changes.empty()) {
                        for (auto [x, y] : changes) {
                            update_vertex(x, y);
                            for (auto [nx, ny] : neighbors(x, y))
                                update_vertex(nx, ny);
                        }
                        k_m_ += heuristic(s_last_, s_start_);
                        s_last_ = s_start_;
                        compute_shortest_path();  // пересчитает МАЛО
                    }
                    old_map_ = msg;
                }
                publish_path();
            });

        path_pub_ = this->create_publisher<nav_msgs::msg::Path>("/planned_path", 10);
    }

private:
    void compute_shortest_path() {
        while (!U_.empty() &&
               (U_.top().key < calc_key(s_start_) ||
                rhs_[s_start_] != g_[s_start_])) {

            auto u = U_.pop();

            if (g_[u] > rhs_[u]) {
                g_[u] = rhs_[u];  // overconsistent → fix
                for (auto s : predecessors(u))
                    update_vertex(s);
            } else {
                g_[u] = INF;      // underconsistent → reset
                update_vertex(u);
                for (auto s : predecessors(u))
                    update_vertex(s);
            }
        }
    }

    void update_vertex(int x, int y) {
        auto id = cell_id(x, y);
        if (id != goal_id_) {
            double min_rhs = INF;
            for (auto [nx, ny] : successors(x, y)) {
                double val = g_[cell_id(nx,ny)] + cost(x,y,nx,ny);
                if (val < min_rhs) min_rhs = val;
            }
            rhs_[id] = min_rhs;
        }
        U_.remove(id);
        if (g_[id] != rhs_[id])
            U_.insert(id, calc_key(id));
    }

    // ... (initialize, detect_changes, publish_path, heuristic, etc.)

    bool initialized_ = false;
    double k_m_ = 0;
    // g_, rhs_ — hash maps: cell_id → double
    // U_ — priority queue с двухкомпонентным ключом
};
Главное в ROS2-интеграции: при каждом обновлении /map (а это ~1-10 раз в секунду от SLAM) нода запускает инкрементальный пересчёт. Не полный A* каждый раз, а обновление только затронутых клеток. На практике это 1–5 мс вместо 50–500 мс.

Плюсы и минусы

Плюсы

  • Быстрое перепланирование — обновляет только затронутые узлы
  • Оптимальный путь гарантирован
  • Идеален для динамических сред (люди, двери, мебель)
  • Стандарт в nav2 (ROS2 Navigation Stack)
  • Работает с реалтайм-обновлениями карты от SLAM

Минусы

  • Сложная реализация — g/rhs, двухкомпонентный ключ, k_m, overconsistent/underconsistent
  • Первый поиск не быстрее A* (выигрыш только при перепланировании)
  • Больше памяти — хранит g И rhs для каждого узла
  • Priority queue с удалением — стандартная std::priority_queue не подходит (нужна своя или std::set)
  • Отладка — сложно, состояния узлов неинтуитивны

Когда использовать D* Lite

Используй D* Lite, если:

  • Карта часто меняется во время движения робота
  • Нужно реагировать на новые препятствия в реальном времени
  • SLAM обновляет карту несколько раз в секунду
  • Робот работает в среде с людьми, дверями, подвижными объектами

НЕ используй D* Lite, если:

  • Карта статична — A* проще и работает так же
  • Нужен any-angle путь — D* Lite даёт сеточные пути (добавь Theta* поверх)
  • Пространство многомерное — используй RRT/RRT*
  • Сложность реализации пугает — начни с A* и добавляй по необходимости

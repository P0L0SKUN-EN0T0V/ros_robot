Шаг 0: Что такое ROS2 и зачем оно

Объясняем с нуля — без предварительных знаний

Зачем роботу программа

Робот — это набор железок: моторы, датчики, камеры, колёса. Сами по себе они ничего не делают. Чтобы робот ехал, объезжал стены и добирался до цели, нужна программа, которая:

  1. Читает данные с датчиков — робот «видит» мир через лидар (лазерный дальномер) и одометрию (счётчик оборотов колёс).
  2. Думает — строит карту, прокладывает маршрут.
  3. Управляет моторами — посылает команды «ехать вперёд», «повернуть на 30°».
Представь пилота самолёта. Он смотрит на приборы (датчики), решает куда лететь (планирование), и двигает штурвал (управление). Программа робота делает то же самое — только автоматически.

Проблема: всё в одном — плохо

Можно написать одну гигантскую программу, которая делает вообще всё: читает лидар, строит карту, ищет путь, рулит моторами. Но это плохая идея:

  • Сломалась одна часть — падает вся программа целиком.
  • Хочешь поменять алгоритм пути? — нужно перелопатить весь код.
  • Работаешь в команде? — все правят один файл и мешают друг другу.
Это как кухня, где один человек одновременно готовит, моет посуду и принимает заказы. Быстрее и надёжнее — разделить на повара, посудомойщика и официанта. Каждый делает своё дело, а общаются через записки (заказы).

Решение: ROS2

ROS2 (Robot Operating System 2) — это не операционная система. Это фреймворк — набор инструментов и правил, которые помогают писать программы для роботов. ROS2 позволяет разбить робота на независимые программы, которые общаются друг с другом.

ROS2 даёт три ключевых вещи:

1. Способ разбить программу на части — каждая часть называется нода (node).

2. Способ связать части между собой — через топики (topics).

3. Готовые инструменты — визуализация, симулятор, логирование, запись данных.

Что такое нода (Node)

Нода — это отдельная программа (процесс), которая делает одну конкретную вещь. У каждой ноды есть имя.

Примеры нод в типичном роботе:

Имя нодыЧто делает
lidar_driverЧитает данные с лидара и публикует их
mapperПолучает данные лидара, строит карту
plannerПолучает карту и цель, ищет путь через A*
controllerПолучает путь, считает скорости для моторов
Нода — это работник на заводе. У каждого своя станция, свой инструмент, своя задача. Они не лезут в дела друг друга, а общаются через конвейерную ленту.

В нашем проекте мы напишем одну ноду global_planner_node, которая будет делать всё сразу: и карту строить, и путь искать, и рулить. Это упрощение для учебного проекта — в реальных роботах ноды обычно разделяют.

Что такое топик (Topic)

Топик — это именованный канал для передачи данных между нодами. Одна нода публикует (publish) данные в топик, другая — подписывается (subscribe) и читает их.
Топик — это радиоволна. Радиостанция (publisher) вещает на частоте 101.5 FM. Любой, у кого есть приёмник (subscriber), может настроиться и слушать. Станция не знает, сколько слушателей. Слушатели не знают друг о друге. Все просто используют один канал.

У каждого топика есть:

  • Имя — строка вроде /scan или /cmd_vel. Слеш в начале — это просто соглашение.
  • Тип сообщения — формат данных, который летит по этому каналу.

Топики в нашем проекте

ТопикТипКто пишетКто читаетЧто внутри
/scan LaserScan Симулятор (Gazebo) Наша нода Массив расстояний от лидара до ближайших объектов (360 лучей вокруг робота)
/odom Odometry Симулятор (Gazebo) Наша нода Позиция робота (x, y) и его ориентация (куда смотрит)
/goal_pose PoseStamped Мы через RViz (мышкой) Наша нода Куда ехать — координаты цели
/cmd_vel Twist Наша нода Симулятор (Gazebo) Команды движения: линейная скорость + угловая скорость
/map OccupancyGrid Наша нода RViz (для отрисовки) Карта мира в виде сетки: 0 = свободно, 100 = стена, -1 = неизвестно
/global_plan Path Наша нода RViz (для отрисовки) Набор точек — запланированный путь от робота до цели

Как всё связано: общая схема

Вот как данные текут в нашем проекте:

Что такое сообщение (Message)

Сообщение — это структура данных с фиксированным набором полей. Каждый топик передаёт сообщения строго одного типа.

Не нужно выдумывать формат самому — ROS2 уже определил стандартные типы. Вот те, которые мы будем использовать:

Twist (команда движения)

Топик: /cmd_vel

geometry_msgs/msg/Twist
├── linear       ← линейная скорость
│   ├── x: 0.2   ← «ехать вперёд со скоростью 0.2 м/с»
│   ├── y: 0.0   ← (для колёсного робота всегда 0)
│   └── z: 0.0
└── angular      ← угловая скорость
    ├── x: 0.0
    ├── y: 0.0
    └── z: 0.5   ← «поворачивать влево на 0.5 рад/с»

Для нашего робота важны только два поля: linear.x (вперёд/назад) и angular.z (поворот влево/вправо).

LaserScan (данные лидара)

Топик: /scan

sensor_msgs/msg/LaserScan
├── angle_min: -3.14     ← начальный угол (рад)
├── angle_max:  3.14     ← конечный угол (рад)
├── angle_increment: 0.0175  ← шаг между лучами (~1°)
├── ranges: [0.5, 0.7, 1.2, inf, ...]  ← массив расстояний
└── ...

ranges — массив из ~360 чисел. Каждое число — расстояние в метрах до ближайшего объекта в данном направлении. inf = ничего не обнаружено (луч улетел в бесконечность).

Odometry (позиция робота)

Топик: /odom

nav_msgs/msg/Odometry
├── pose.pose.position
│   ├── x: 1.5    ← робот находится в точке x=1.5 м
│   └── y: 2.3    ← и y=2.3 м
└── pose.pose.orientation
    └── (кватернион → угол)  ← куда робот «смотрит»

Из ориентации (кватерниона) мы извлечём угол yaw — направление, куда повёрнут нос робота.

Pub / Sub: как ноды общаются

Механизм «публикация-подписка» (publish-subscribe, или pub/sub) работает так:

1
Publisher создаёт топик — нода говорит: «Я буду публиковать данные типа LaserScan в топик /scan».
2
Subscriber подписывается — другая нода говорит: «Когда в /scan появятся новые данные — вызови мою функцию scanCallback».
3
Данные текут автоматически — publisher пишет, subscriber получает. Никто никого не ждёт. Если subscriber не успел — пропустит сообщение (и это нормально).
Это как YouTube-канал. Автор загружает видео (publish). Подписчики получают уведомления (subscribe). Автор не знает, кто конкретно смотрит. Если ты отписался — автор продолжает загружать. Если подписался — получаешь новые видео автоматически.

Ключевое преимущество: Publisher и Subscriber ничего не знают друг о друге. Можно заменить одну ноду другой, и всё продолжит работать — если формат сообщений совпадает. Это как USB: не важно, какая мышка — главное, чтобы разъём подходил.

Как это выглядит в коде (C++)

Не пугайся — сейчас просто посмотри на общую структуру. Детали разберём позже.

// Подключаем ROS2
#include <rclcpp/rclcpp.hpp>
// Подключаем типы сообщений
#include <sensor_msgs/msg/laser_scan.hpp>
#include <geometry_msgs/msg/twist.hpp>

// Наша нода — это класс, наследник от rclcpp::Node
class MyRobot : public rclcpp::Node {
public:
    MyRobot() : Node("my_robot_node") {

        // Подписываемся на /scan (данные лидара)
        scan_sub_ = this->create_subscription<sensor_msgs::msg::LaserScan>(
            "/scan", 10,
            [this](sensor_msgs::msg::LaserScan::SharedPtr msg) {
                // Эта функция вызывается каждый раз,
                // когда Gazebo присылает новые данные лидара
                RCLCPP_INFO(this->get_logger(), "Лидар: %zu лучей", msg->ranges.size());
            }
        );

        // Создаём publisher для /cmd_vel (команды движения)
        cmd_pub_ = this->create_publisher<geometry_msgs::msg::Twist>(
            "/cmd_vel", 10
        );
    }

private:
    rclcpp::Subscription<sensor_msgs::msg::LaserScan>::SharedPtr scan_sub_;
    rclcpp::Publisher<geometry_msgs::msg::Twist>::SharedPtr cmd_pub_;
};

Не надо заучивать! Этот код — шаблон. В следующих шагах мы соберём его по кусочкам, и каждую строчку объясним. Сейчас важно понять общую идею: нода создаёт подписки (получать данные) и паблишеры (отправлять данные).

Что пишем мы, а что уже готовое

Это самый частый вопрос новичков: «А откуда берётся лидар / карта / симуляция?»

КомпонентКто его делаетНам нужно
Симуляция мира (стены, комнаты) Gazebo (готовое) Только запустить
Робот (TurtleBot3) Пакет turtlebot3_gazebo (готовое) Только запустить
Данные лидара (/scan) Gazebo автоматически публикует Только подписаться и читать
Позиция робота (/odom) Gazebo автоматически публикует Только подписаться и читать
Визуализация (карта, путь) RViz (готовое) Только публиковать данные в нужном формате
Построение карты Мы пишем! Функция updateMapWithLaser
Поиск пути (A*) Мы пишем! Функция planAStar
Управление движением Мы пишем! Функция purePursuitControl

Итого: из всей системы мы пишем только один файл — ноду global_planner_node с тремя ключевыми функциями. Всё остальное (симулятор, робот, лидар, визуализация) — уже готовое и работает из коробки.
